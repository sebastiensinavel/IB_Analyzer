1. Le principe

Tout le métier tourne dans le navigateur. Transactions, positions, journaux, couverture, alertes et jetons Flex vivent dans l'IndexedDB du navigateur. Le serveur authentifie, relaie Flex quand le compte l'autorise et garde au plus un blob chiffré qu'il ne sait pas lire. L'agent local, optionnel, fournit des données brutes de TWS.

Conséquences directes :

  • L'application fonctionne sans connexion et même serveur coupé (Service Worker) ; la connexion n'ouvre que le proxy Flex et la sauvegarde.
  • Le code métier est écrit en TypeScript pur, sans framework, dans des paquets packages/* testables isolément.
  • apps/api n'a aucune table de portefeuille, et n'en aura jamais.

3. L'application embarquée dans le navigateur

Le SPA est construit en couches. Le sens des dépendances est strict : l'interface dépend des moteurs, jamais l'inverse ; @ib/ledger ne dépend de rien.

Démarrage

main.tsx applique le thème stocké, branche le rechargement sur changement de Service Worker et de schéma Dexie, puis passe par startApp (src/startup.ts) : en mode démonstration, la base ib-analyzer-demo est semée avant le premier rendu, puis l'application est montée — même si la graine échoue — et le veilleur d'alertes démarre.

Ce qui est calculé, jamais stocké

Le stockage ne contient que des faits importés. Tout le reste est une vue recalculée à chaque changement de la base (useLiveQuery de Dexie) : journaux de stratégie, positions par stratégie, rapport de risque et couverture, capital et rendements, totaux, stratégie de chaque ligne de l'Historique, alertes automatiques, niveaux dessinés sur les graphes.

Trois sources, propriété de plage

L'historique arrive par trois chemins — relevé HTML, Flex, agent — et se fusionne par propriété de plage, jamais par comparaison de contenu : Flex possède ses jours, le relevé n'écrit qu'avant, l'agent qu'après (en jour de marché New York).

5. Les paquets métier

Consommés en source (workspace:*, exports vers src/index.ts) : rien n'est construit avant usage, Vite les compile avec l'application.

@ib/ledger aucune dépendance

Le modèle : Transaction, Position, import et filtre par propriété de plage (filter.ts, marketDayOf), solde de cash calé sur les Cash Reports, totaux par devise. Le sous-dossier journals/ rejoue le ledger en journaux Wheel, LEAPS, Condors et Autres : carnet de lots, fusion des tranches, inférence des assignations et expirations, opérations sur titres, ordre de sortie des lots, capital, statistiques.

@ib/ib-parsers ledger, @noble/hashes

Parseurs des trois sources : réponse Flex XML (et son enveloppe), relevé d'activité HTML, charges utiles de l'agent. Identité des contrats (conid, ISIN, symboles OSI), conversion des heures IB (heure murale New York), rapport des lignes ignorées.

@ib/coverage ledger

Moteur de couverture des options vendues (cash, actions, LEAPS, spread), rapport de risque, décision de rachat (evaluateBuyback), positions par stratégie et par condor, encadrés des pages de stratégie, suggestions de position, valeur de liquidation.

@ib/alerts ledger

Alertes de prix : automatiques (call couvert sous le prix d'assignation, aile vendue d'un condor) calculées depuis les journaux, manuelles évaluées sur les cotations, ancrage S₀ à la vente.

@ib/ui base-ui, lucide

Composants shadcn générés puis rendus relatifs (aucun alias @), partagés par l'application.

7. Stockage local (IndexedDB)

Une base ib-analyzer par origine (ib-analyzer-demo en démonstration), qui appartient au navigateur et non à un compte serveur. Schéma Dexie en douze versions (src/db/schema.ts).

TableCléContenu

transactions[accountId+externalId]Le ledger, toutes sources confondues.
contracts[accountId+conid]Identité des contrats, fusionnée import après import.

9. Le serveur Django (apps/api)

Django 5.2 LTS sur Python 3.14, API en django-ninja (schéma OpenAPI exporté vers le client), authentification django-allauth en mode headless avec 2FA (TOTP), gunicorn et whitenoise, httpx pour appeler IB.

AppModèlesEndpoints
coreUser, Invitation, Backup (octets chiffrés, taille, date)/invitations/accept, /backup (GET, POST, DELETE), /backup/status
ibaucun/flex/send-request, /flex/get-statement : proxy sans état, limité en débit, jeton jamais journalisé
config—/health, /csrf ; /_allauth/… pour la session

10. L'agent local (apps/tws-agent)

Paquet Python ib-tws-agent installé par uv depuis la roue servie sous /agent/. FastAPI + uvicorn sur 127.0.0.1:8100, CORS limité aux origines de sa configuration (ib-tws-agent origin add), connexion à TWS par ib_async en clientId 0. Il ne stocke rien.

EndpointRend
GET /healthPrésence et version.
GET /snapshotPositions, exécutions du jour, P&L du jour (reqPnLSingle).
GET /barsDeux ans de barres journalières TRADES d'un sous-jacent.
GET /quoteslast et close différés des actions et indices demandés.
POST /flex/send-request, /flex/get-statementRelais Flex, jeton dans le corps de la requête.

11. Outillage, tests, déploiement

  • Monorepo : pnpm (Node 22) pour apps/* et packages/*, uv pour les deux projets Python. Lint par oxlint, typage tsc -b.
  • Tests : Vitest à côté du code (fake-indexeddb, Testing Library, jsdom), oracles rejoués sur des corpus IB anonymisés, pytest pour l'API et pour l'agent (sur un FakeIB), Playwright en bout en bout et pour le Service Worker contre un vrai build.
  • pnpm check : lint, typage, fraîcheur des types d'API, build, tests TypeScript.
  • Déploiement : VPS, un Traefik partagé, deux piles Docker Compose (iba-prod, iba-dev) avec nginx pour le SPA, Django et PostgreSQL ; exploitation par deploy/iba. Détails dans docs/deploiement-vps.md.
